## 0. 결론 먼저

이 ws(`kimkh-17U70N-GA70K`, 개인PC)의 git 이력 + `md/`만으로 **"실기 검증 + 오류→원인→수정" 스토리는 바로 만들 수 있다.**

## 3. GPU PC 로그 — 있다. 이 저장소엔 없다

질문: "gpu pc에서만 있는 로그가 따로 있을까?" → **있을 가능성이 높고, 지금 이 repo에서는 안 보인다.**

확인한 근거:
- 지금 세션 `hostname` = `kimkh-17U70N-GA70K` (GPU 없는 개인PC). 프로젝트 CLAUDE.md 4절 기준 GPU 실기 머신은 `rokey`(RTX 4060) — **다른 머신**이라 여기서 직접 확인 불가.
- `.gitignore:77` — `isaac_ros-dev/` 자체가 통째로 git 추적 제외. 이 머신에 로컬로 존재는 하지만(`~/cobot2_ws/isaac_ros-dev/src`) **git 이력에 없고**, `rokey`에 있는 버전과 동일하다는 보장도 없음(미확인).
- `.gitignore:82` — `isaac_ros-dev_export/`(docker 이미지 tar, 19GB+)도 제외.
- `.gitignore:4,29,32,64` — `log/`, `*.bag`, `rosbag/`, `*.log` 전부 제외. nvblox/FoundationPose/GraspGenX 실행 로그, rosbag 캡처는 **구조적으로 이 repo에 안 들어온다.**
- `md/plans/2026-08-01-pc-role-split.md` — Day4(FoundationPose, GraspGenX), Day5(통합 10회 반복)가 **GPU PC 전용**으로 명시돼 있음. 이 작업들의 원본 실행 로그·docker 컨테이너 로그는 GPU 머신(`rokey`) 또는 `md/plans/2026-08-04-gpu-rental-checklist.md`가 말하는 **원격 렌탈 GPU(AWS/Lightning, 세션 종료 시 소멸 가능)** 위에만 있었을 것.
- 반대로 **이미 git에 들어온 GPU 결과물**도 있다 — `md/2026-08-07-nvblox-curobo-digest.md`, `md/isaac_ros_nvblox_setup.md`, `md/detect_graspx.md`(8.85ms 벤치마크)는 GPU 세션 결과를 사람이 손으로 요약해 옮겨 적은 **다이제스트**다. 원본 로그가 아니라 요약이라는 점은 인지하고 쓸 것.

**결론**: 이 repo만으로는 "GPU 쪽에서 원본 로그가 뭐가 있었는지" 전체를 알 수 없다. `rokey` 머신 또는 렌탈 GPU 세션의 결과물(docker 컨테이너 로그, rosbag, 스크린 기록)이 로컬에 남아있는지는 **그 머신에서 직접 확인해야 한다** — 여기서 추측 못 함.

## 3-2. 더 수집하면 좋을 데이터 — **이미 계획된 실기 세션에서 공짜로 나온다** (2026-08-09 추가)

> §0의 "정량 비교는 지금 데이터로 안 된다"는 **지금 시점의 사실**이지 영구 제약이 아니다.
> 앞으로 할 실기 작업 두 개가 그 빈칸을 그대로 채운다 — **그때 기록만 남기면 된다.**
> 지나가면 다시 뽑으려고 실기 세션을 또 잡아야 한다. 그게 이 절의 요점이다.

| 발표에서 비어 있는 축 | 어느 작업에서 나오나 | 그때 반드시 남길 것 |
|---|---|---|
| **플래너 성능 비교** (OMPL vs cuMotion) | [[ws/cobot2/plans/2026-08-09-cumotion-verify]] T1~T7 | 장애물이 **궤적을 실제로 막는 씬**에서의 성공률·계획시간. 08-06의 관절목표 42.4/110.6 ms는 OMPL에 유리한 조건이라 **발표에 그대로 쓰면 안 된다**(state.md 경고) |
| **인식 성능 before/after** | [[ws/cobot2/plans/2026-08-09-yolo-seg-finetune]] | 같은 씬을 COCO 가중치 / 파인튜닝 가중치로 각각 돌린 `/yolo_seg/overlay` 캡처 + 검출 수. **"COCO엔 우리 물체가 아예 없다 → 직접 학습시켜 잡았다"**는 서사가 그림 두 장으로 끝난다 |
| **파지 성공률** | 파인튜닝 이후 실기 pick 반복 | 시도/성공 횟수와 실패 원인 분류. 표본 10회라도 "표본 10회"라고 적으면 정직한 수치다 |
| **캘리브 오차** | state.md "다음 할 일" 3번 | 현행 캘리브는 자체 진단 **불합격**(병진잔차 중앙값 40.1 mm). 이 숫자 자체가 "측정하고 불합격 판정을 내렸다"는 좋은 소재다 — 숨기지 말고 §1-3의 before/after 프레이밍으로 쓴다 |

**추가 수집 비용이 거의 0인 것들** (실기 세션에서 명령 한 줄씩):

- 파인튜닝 캡처 세션의 `rgb.png`/`seg.png` 쌍 — 어차피 학습 데이터로 저장된다. 그중 몇 장이 **"depth 세그가 라벨을 자동 생성한다"**는 방법론 그림이 된다 (사람 라벨링 0회가 이 프로젝트의 셀링 포인트다)
- `/yolo_seg/overlay` 스크린 캡처 (`publish_overlay:=true`, rqt)
- 실기 세션 시작·종료 시각 (작업 소요시간 축)
- 실패 로그 원문 — `errors-log.md`가 이미 하는 일이지만, **터미널 원문 1~2장**이 슬라이드에서 요약보다 강하다

> ⚠️ **없는 수치를 만들지 않는다**는 §0·§2의 원칙은 그대로다. 이 절은 "지금 없으니 포기"가
> 아니라 **"곧 생기니 그때 버리지 말자"**는 목록이다.
